### 2. Root cause of "mouse moves when focus changes" (ct4 fix)
- Symptom (user): when focus leaves the game to the window below, the cursor
  teleports to the **center of the screen**.
- Evidence: `~/.config/hypr/game-overlays.lua` focus log
  (`/tmp/bar-avoid.log`) showed a `steam_app_4126220`/`steam` focus BOUNCE loop
  during the game (22:10:37), cursor converging on ~960,538 (~center).
- Mechanism found in source (`src/desktop/view/Window.cpp`):
  - X11 `_NET_ACTIVE_WINDOW` client message → `CWindow::activate()` (XWM.cpp:
    `XSURF->m_events.activate.emit()`).
  - `activate()` → `fullWindowFocus()` + `warpCursor()` →
    `Pointer::pointerController()->warpTo(middle(), force)`.
  - The game is a floating full-monitor overlay at 0,0, so its `middle()` ==
    screen center (960,540). Every time the game lost focus it re-requested
    activation, and Hyprland (default `misc:focus_on_activate=1`) honored it:
    stole focus back AND warped the cursor to center.
  - `rawWindowFocus()`/`rawSurfaceFocus()` do NOT warp — the warp is purely the
    `activate()` path.
- Fix (1 gate in `CWindow::activate()`):
  ```cpp
  if (TrustedClickthrough::isTrusted(this))
      return;
  ```
  placed right after the already-focused check. Root-trusted overlays can never
  self-activate, so they can't steal focus or warp the cursor. User-initiated
  focus (hover/click on opaque pixels via the input shape) still works through
  the normal `rawWindowFocus` path — that path goes through `activateWindow()`,
  NOT `activate()`, so the game still gets told it's active correctly.
  Existing `suppress_event` per-window still applies for finer control.
- Deliberately NOT re-applied: ct3's `InputManager.cpp` change (hover-focus
  falls through a layer). That was the wrong direction — it pushed keyboard
  focus around on hover and fought the game; rollback removed it.
