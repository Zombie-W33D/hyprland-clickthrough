## What ct6 = ct3 + two delta hunks (the "re-fix")

ct3 already had everything the user wants (hover-focus falls through a trusted
transparent overlay, no `activate()` gate). ct5's ONLY functional difference
from ct3 was ct4's gate; **ct3 and ct5 were otherwise code-identical**. So the
bleed of ct4/ct5 is:
- `src/desktop/view/Window.cpp` (re-derived from ct4, re-reviewed fresh):
  in `CWindow::activate(bool force)`, right after the already-focused check:
  `if (TrustedClickthrough::isTrusted(this)) return;`. This is the cursor-teleport
  fix: the game re-requests `_NET_ACTIVE_WINDOW` whenever focus drifts off it;
  honoring it walks `fullWindowFocus()` + `warpCursor()` → cursor lands in the
  middle of a full-screen overlay = screen center. Blocking self-activation for
  root-trusted overlays kills the warp AND the focus-steal-back. User-initiated
  focus (hover/click on opaque pixels) uses `rawWindowFocus`/`activateWindow`,
  NOT `activate()`, so clicks on the game still work.
- `src/xwayland/XShapeInputRegion.cpp` + `src/xwayland/XWM.cpp` (NEW, ct6):
  the REAL fix for "no autofocus passing down" (see Root cause below).

## Root cause: shape-kind flip-flop (why ct5 looked dead)

Debugging on this machine found the actual blocker, which ct3/ct4/ct5 all had:
- `XShapeInputRegion::syncInputRegion` only read the **INPUT** shape kind
  (`XCB_SHAPE_SK_INPUT`).
- Wine/GE exports the layered-overlay per-pixel mask (~250K px in ~400 tiny
  rects, re-shaped every second as the game animates) on **whichever kind it
  feels like** — I watched it live swap between CLIP (~388 rects, INPUT full)
  and INPUT (~400 rects, CLIP full) within minutes, plus the full-window
  default at other times.
- When the mask sat in CLIP, the compositor saw "input region = whole 1920x1080"
  → `isClickThroughAt()` false everywhere → `windowAt` never fell through → no
  click-through, no hover-focus-down, in ANY build including ct3. That's the
  "no autofocus yet passing down" report on ct5 (and it would have hit ct3 too
  at whatever moment you looked).
- Fix: `syncInputRegion` now reads INPUT first; if it's the full-surface default
  (1 rect == entire surface) or empty, it reads CLIP; a genuine mask is anything
  NOT the full-surface single rect. Empty mask on both ⇒ reset to compositor
  default (`inputIsInfinite=true`) as before. `xcb_shape_select_input` now
  subscribes to INPUT|CLIP kinds, and `CXWM::handleShapeNotify` accepts both
  kinds instead of only INPUT, so mask moves between kinds re-sync instantly
  without waiting for a commit.
