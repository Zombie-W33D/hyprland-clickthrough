## Why ct6 has two extra hunks on top of ct3 (and why ct3/ct4/ct5 "felt dead")

Everything was suspended on a false assumption: **the patch only read the XShape
INPUT kind.** Live probes of the game window (X11 id **0x05800004**; leading
zero mandatory — `0x58000004` is a different number, BadWindow) showed Wine/GE
exports the per-pixel alpha mask (~250K px in ~400 tiny rects, re-derived every
second) on whichever shape kind it wants, and it FLIPS between:
- `SHAPE_INPUT` = the mask, `SHAPE_CLIP` = 1 full rect (`n=1 area=2073600`), and
- `SHAPE_CLIP` = the mask (~388 rects), `SHAPE_INPUT` = 1 full rect, and
- both briefly at the full-window default at certain game UI states.

When the mask sits in CLIP, the compositor's input region = whole screen →
`isClickThroughAt()` false everywhere → no fall-through → "no autofocus passing
down" on ct3/ct4/ct5 at whatever moment you observed it. Therefore a pure ct3
install would still look broken whenever CLIP held the mask — that's why ct6
fixes the SOURCE of the mask as well as the teleport.

ct6 = ct3 +
1. `src/xwayland/XShapeInputRegion.cpp` — `syncInputRegion` reads INPUT first;
   if INPUT is a single rect spanning the full surface ("no mask"), read CLIP;
   a genuine mask is anything != full-surface single rect. Both empty ⇒ reset to
   compositor default (`inputIsInfinite=true`) exactly like before. Also
   `xcb_shape_select_input` now subscribes to INPUT|CLIP kinds (both).
2. `src/xwayland/XWM.cpp` — `handleShapeNotify` accepts CLIP-kind events too
   (was: only INPUT), so kind flips re-sync instantly without waiting for commit.
3. `src/desktop/view/Window.cpp` — `CWindow::activate(bool force)`: early return
   `if (TrustedClickthrough::isTrusted(this)) return;` right after the
   already-focused check. Cure for the cursor-teleport: the game re-requests
   `_NET_ACTIVE_WINDOW` whenever focus drifts off it; honoring it runs
   `fullWindowFocus()` + `warpCursor()` → cursor lands mid-screen. Blocking
   self-`activate()` for root-trusted overlays kills the warp AND the steal-back.
   Focus via hover/click uses `rawWindowFocus`/`activateWindow`, NOT `activate`,
   so clicks on opaque pixels never go through this path. (Same gate ct4 had;
   re-derived and re-reviewed, remains WIN-worthy.)

ct3 already carried (keep in mind, unchanged): the `OVERLAY_OFF_POINTER` bypass in
`src/managers/input/InputManager.cpp` `mouseMoveUnified` (~lines 715-718) —
source of hover-focus-fall-through when the input region shows transparent; and
`Desktop::isClickThroughAt` (ViewHitTester). CT5 was functionally identical to
ct3 except for ct4's gate; ct4/ct5 documents mis-attributed ct3 to "the other
model" — FALSE, git proves ct3 authors = the same local `zombie@w33d` /
`mjthorene@gmail.com` as ct1/ct2 (commits 2026-09-11 21:49 / 22:52).

## The bar-avoidance piece (user: this is what accidentally fixed autofocus)

`~/.config/hypr/game-overlays.lua` (repo copy: `game-overlays.lua.example`) does
the Omarchy-bar avoidance: overlay is a normal floating XWayland window, bars
reserve no space for floating windows, so the script reads the live layer
geometry of layer-shell namespace `omarchy-bar` and resizes+offsets the overlay

- `bar_avoid_all()` call on first poll after reload.
